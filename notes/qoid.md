# 跨帧字典解码器（`DECODER_TYPE 6`，实验）

> 把"该帧槽上次解出来的那条带"的 QOI 流当 deflate 字典，用自写的 `tinyd` 解压，
> 拿到脏矩形 −42~−86% 的载荷收益；**但它在持续负载下会静默冻结，不能合进默认配置**。
> 2026-10-02 续查把根因指向**显示总线上唯一没有超时的等待**
> （`dma_channel_wait_for_finish_blocking`，见"危险项"一节），**待真机验证**；
> `tinyd` 已被宿主机模糊测试排除。

## TL;DR

- 机制：字典是**该槽位上次解出来的那条带**，不是"上一帧同带"；元数据放在载荷内部的 16 B 子头里，**没有改 `struct pud_ep1_header`**。
- `tinyd`（`src/decoders/tinyd/`）= stored + 固定 Huffman + LZ77，**动态 Huffman 明确拒绝**；固定 Huffman 解码比动态省 18%（15.5 对 18.9 周期），主频上完全线性。
- 载荷：脏带较大时 −42.2%、较小时 −78.9%、单条带小改动 −86%~−97%；**整屏重发的垂直增量收益不成立**（载荷只降 3.0%，帧时间没改善）。
- **危险项**：持续负载下偶发**静默冻结**（`submitted` 继续涨、`drawn` 停住、`dropped == 0`，没有任何计数报警）；两次真实发生约在 3 与 63 次提交处，约 15,000 次发送未能复现。
  **2026-10-02 进展**：两次现场都是 `submitted − drawn == 3`（槽全满）⇒ 解码任务卡在 `decoder_drawimg_slot()` **内部**；`tinyd` 经宿主机 ASan/UBSan 模糊测试（全部截断前缀 + 8000 次变异）**已排除**；绘制路径上唯一**无超时**的等待是 `tft_async_video_wait() → dma_channel_wait_for_finish_blocking()` ⇒ 头号嫌疑。
  由此**推翻了原建议**："解码任务里复位游标"的看门狗**不可能触发**（任务正是被卡的一方）；且原先"type-6 特有"的判断建立在 1/250 的估计上，按实测 1/15000，那组 1080 次对照 **没有排除共用通路**。
  **在真机验证并修好总线之前，这个解码器不算可用**。
- 协议两侧**已同步**（驱动仓权威文档有 `0x03`–`0x05` 与 `decoder_type=6`、16 B 子头与分带约束），**驱动也已实现 6 并在真机上跑通**：kiosk 连续 4490 条带、`qoid_bad == 0`、`dropped == 0`。`0x03`–`0x05` 三条命令驱动仍不发送。

## 为什么与怎么设计

帧时间是链路决定的（链路约 0.9~1.1 MB/s，一帧整屏 74~100 ms，解码只占 ~26 ms），所以**唯一
值钱的东西是字节**；而桌面内容最大的冗余不在帧内、在**帧与帧之间**（同一个字形、同一段没变的
UI）。QOI 与帧内 deflate 都看不到它。

**载荷收益**（主机侧、同一份合成桌面内容，帧 B 只有几个脏矩形）：

| 情形 | 无字典（≈普通 QOIZ） | 跨帧字典（每条带用上一帧同带做 zdict） |
| --- | --- | --- |
| 脏带，改动较大（4 条带，QOI 43812 B） | 32744 B | **18939 B（−42.2%）** ⇒ 省 14.7 ms/帧 |
| 脏带，改动较小 | 32744 B | **6899 B（−78.9%）** ⇒ 省 27.5 ms/帧 |
| 单条带里冒出一个 UI 元素 | — | QOI 11270 B → deflate **3464 B（−69%）** |

⇒ 收益正比于"该带里没变的比例"，而这正是局刷的形状。项目自己的合成桌面里"面板条"那一格是
**1334 → 300 B（−77%）**。

**解码代价**（独立探针固件，`copy_to_ram` 排除 flash，crc32 校验，同一颗 RP2350）：

```
clk 150 MHz: 129 ns/输出字节 (19.4 周期)   crc ok
clk 225 MHz:  86 ns/输出字节 (19.35 周期)  crc ok
clk 300 MHz:  64 ns/输出字节 (19.2 周期)   crc ok
clk 384 MHz:  50 ns/输出字节 (19.2 周期)   crc ok
no dict   : inflate rc -3 (Z_DATA_ERROR), 0 字节   ← 不给字典就解不动，证明码流真的引用了上一帧
```

单位成本恒为 19.2~19.4 周期/输出字节 ⇒ 解码能力**严格随主频线性增长**（150→384 MHz 快 2.6×）：
一帧整屏（93738 B 输出）的解码是 12.1 / 8.1 / 6.0 / 4.7 ms（520 MHz 外推 3.5 ms），全部藏在
45~74 ms 的传输窗口里。**只做固定 Huffman 就够**：`strategy=Z_FIXED` 的代价只有 **+10.3% 字节
（0.8 ms/帧）**，解码器不必实现动态 Huffman 表。

### `tinyd`：自写的字典解压核心（2026-10-01 实测）

上面那 19.2 周期是 zlib `inflate` 自带 32 KB 窗口 + ~7 KB 状态换来的（≈40 KB RAM）。本项目
不需要通用 inflate：**只用固定 Huffman + caller 给的窗口**就够，于是写了 `tinyd`（≈200 行，
stored + 固定 Huffman + LZ77，动态 Huffman **明确报错拒绝**而不是静默解错）。

三方**同源**实测（同一份载荷、同一颗 RP2350、同一轮时钟扫描、三条路径都 crc ok；载荷是同一条
带，输出 11270 B；动态 Huffman 3464 B / `Z_FIXED` 3846 B，**+11.0%**）：

| 路径 | 150 MHz | 225 MHz | 300 MHz | 384 MHz |
| --- | --- | --- | --- | --- |
| zlib / 动态 Huffman | 126 ns/B (18.90 周期) | 84 (18.90) | 63 (18.90) | 49 (18.81) |
| zlib / 固定 Huffman | 104 ns/B (**15.60**) | 69 (15.52) | 52 (15.60) | 40 (15.36) |
| **tinyd** / 固定 Huffman | 106 ns/B (15.90) | 71 (15.97) | 53 (15.90) | 41 (15.74) |

1. **固定 Huffman 比动态更省解码周期**（15.5 对 18.9，−18%）—— 省掉的是建表。所以 `Z_FIXED`
   的代价**只有链路上的那 11% 字节**，解码侧反而更快。
2. **`tinyd` 只比 zlib 的手写 inflate 慢 2.5%**（15.90 对 15.52）：`tinyd` **2.4 KB 代码 +
   3 KB 表**，zlib 那条路 **14.1 KB 代码 + 40 KB 窗口/状态**。
3. 单位成本在主频上**完全平**（15.9±0.1）⇒ 超频收益直接线性拿到。

宿主机对拍 **204 例全过**：4 个命名用例（带字典 / 不带字典 / 全 stored / 动态必须拒绝）
+ 200 例"历史与目标共享大量内容"的随机用例。带字典那条带上 **21000 B 目标：有字典 520 B、
无字典 1301 B**。

### 必须记住的语义差异

`zlib` 不给字典会 **rc −3 失败**，而 `tinyd` 拿一块**清零**的窗口当历史**照样 rc 0、解出
11270 字节** —— 匹配落在窗口内就是"合法"的，**字典错/丢帧导致的错位解不出来**，只会变成花屏。
⇒ 协议**不能指望解码器发现字典不对**，必须由**显式状态**保证（`dict_serial`/`dict_len` 校验），
与既有流控一样属于"宁可拒绝也不静默出错"那一类。

## 固件原型

固件侧已完成（`src/decoders/tinyd/` + `decoder.c` 的 `DECODER_USE_QOID`）：

- 每帧槽一块窗口 `PUD_DELTA_WIN`（默认 32 KB，RP2040 16 KB），布局 `[历史][输出]`；
  两块板都编得过：RP2350 `data+bss` 464 KB / 520 KB，RP2040 203 KB / 258 KB
  （窗口 3 × 32 KB；RP2040 用 3 × 16 KB）。上板后设备以 `2e8a:0001` 正常枚举。
- **字典不是"上一帧同带"，而是"该槽位上次解出来的那条带"**。留一整帧做字典要 94 KB
  （实测整屏 QOI 93893 B）到 460 KB（最坏情况），现有余量放不下。
- **字典元数据放在载荷内部的 16 字节子头里**：`magic('PUDD') / flags / reserved / dict_serial /
  dict_len`，之后才是 raw deflate 流；**没有动 `struct pud_ep1_header`**（那是所有解码器共用的
  协议字段，为一次实验改它要连驱动和两个仓库的文档一起改）。
- **设备按载荷报的条带序号在自己的窗口里找字典**：找到就用它当字典并写回该窗口，找不到才
  `qoid_mismatch++`。主机取"**最近一条同矩形的已发条带**"；找不到同矩形时退而用**正上方**那条
  （整屏重发时）。
- 三种失败各自计数：`g_decoder_stat_qoid_bad` / `qoid_mismatch` / `qoid_oversize`。

## 上板实测（2026-10-01，同一块板、同一份内容）

**轮转游标那版（已回退）**：把槽位分配从"最小空闲"改成轮转游标确实修好了 DELTA（慢主机
`qoid_mismatch 0`、`hist_bytes = 12 × 11732`；A/B `hist_bytes = 24 × 11730`），**但在整屏负载下
把流水线卡死**：`--full` 跑到一半主机 `bulk_write` 超时，设备 `submitted 303 / drawn 300 /
dropped 0`，`decoder_task` 阻塞在等信号量、PC 落在 `prvIdleTask`（不是 HardFault）。⇒ 已整段
回退，共用流水线恢复"最小空闲槽 + 最低忙槽"，默认 `DECODER_TYPE=3` 复验通过
（整屏四种图案 `1360 == 1360`、`dropped 0`、0.94 MB/s）。**结论：槽位归属不能靠调度顺序约定**。
游标版上测到的 DELTA 数据仍有效：一条 480×16 纹理带，键帧 11053 B / 12.68 ms 对
DELTA **3389 B / 0.92 ms**（墙上 16.53 → 4.72 ms，3.5×），设备侧 `hist_bytes 281520 = 24 × 11730`
（24 条 DELTA 全部被接受并用字典解出 —— `hist_bytes` 是"设备真的用了字典"的硬证据）。

**第四轮起（当前实现）**：DELTA 不再依赖流水线是否打满。慢主机（每条带一个来回，正是之前
8/15 误拒的用例）`qoid_mismatch 0`、`hist_bytes = 164240 = 14 × 11731`、`submitted == drawn`。
整屏重发的**垂直增量**也已接上并上板：`submitted 104 == drawn 104`、`mismatch 0`、
`hist_bytes = 318012`（除首帧外 96 条全都用了字典）。**但收益不成立**：载荷只降 **3.0%**
（`8 key / 0 delta, 81574 B` → `2 key / 6 delta, 79118 B`；三帧合计 112260 → 96798 B，−13.8%），
帧时间没有改善（首帧 21.57 ms、其后 22.26 ms；墙钟还含主机编码）⇒ 别指望整屏重发靠它变快，
值钱的仍是**同一矩形**那条（脏面板条 −86%、文本行 −97.9%）。

**第五轮起发现窗口边界**：换成噪声/照片型内容（每条带 QOI 60 KB）后 `qoid_oversize` 涨到
**78**（104 条里 78 条被拒），`hist_bytes` 归零，面板对应区域**不更新** —— 这是
`PUD_DELTA_WIN`（32 KB ⇒ 半窗 16 KB）只装得下桌面包的必然结果；设备**拒收而不是截断**。
缩带宽实测有效：把主机 `band_pixels` 设成最坏情况安全的 **5456 px（480×11 = (16384−16)/3）**，
发纯噪声整屏，`qoid_oversize` 从 78 → **0**、`submitted 60 == drawn 60`、`dropped 0`；
代价是一帧噪声 **738 / 805 ms**（60 条带）。**窗口限制的是每条带的字节数，不是分辨率**。

**第六/七轮：字典与解码赛跑，固定距离规则被实测否定**。第六轮发现"字典 = 紧邻的上一条"会跟
解码赛跑（`qoid_mismatch 17/20`）：解码是异步的，主机发得比解码快时那条带**还没进窗口**。
第七轮试固定距离：距离 1 拒 **17/20**、距离 3 拒 **5/20**、距离 4 拒 **8/20** ——
**任何固定距离都不成立**，因为"还没解完"的下界是流水线深度、"已经被挤出"的上界也是它，
**两个边界重合，可靠区间是空的**。但 DELTA 本身成立：两个真实负载都没问题（慢主机
12/12 全中、整屏 96/96 全中）—— 出问题的只是"故意发得比解码快"的压力测试，而真实主机每条带
光编码就要 1.3 ms，比 0.18~0.4 ms 的发送慢一个数量级，**主机天然是"慢"的一方**。
真实可用的档位：键帧 332 B / 0.53 ms 发送，DELTA **150~160 B / 0.36~0.43 ms 发送**
（−55% 载荷、−20~30% 发送）。

**第九轮：同板、同负载、同量具的 qoiz vs qoid 直接对比**（一条 480×24 脏面板条每帧动一个小块，
20 帧；主机编码全部排除在计时外；qoiz 一侧用 libdeflate，对 qoid 是保守的比法）：

| 固件 | 载荷 | 仅发送（中位数） | 主机编码 | 设备侧 |
| --- | --- | --- | --- | --- |
| `DECODER_TYPE 5` qoiz + libdeflate | 315 B/条带 | **0.52 ms**（0.40~0.64） | 1.37 ms | `20/20`、`dropped 0` |
| `DECODER_TYPE 6` qoid | **150 B/条带** | **0.36 ms**（0.14~0.60） | 1.36 ms | `20/20`、`dropped 0`、`mismatch 6` |
| | **−52.4%** | **−30.8%** | ≈0 | 6 条被拒（脚本故意不等解码） |

主机编码两边一样（1.36 / 1.37 ms）⇒ "字典让主机变慢"不存在。RAM：qoid **464 KB** 对
qoiz+libdeflate **~441 KB**，多花 **~23 KB**（3 × 32 KB 窗口 − 省下的 64 KB `qoiz_buf`）。
那 6 条 `mismatch` 只会让收益被低估，不会高估。**反过来整屏重发是 +14.8% 更差**。

**第十轮：把推算拿去测，两处被修正**。发送时间**不是字节主导而是按像素**（8/16/32/45 行：
152/222/342/432 B 对应 0.204/0.355/0.720/1.069 ms，斜率 ≈ **49 ns/px**）⇒ 这些尺寸下主导项是
设备侧解码+刷屏加流控等待，不是链路。**"每次传输固定开销 0.18 ms"是错的**（实测规模
~0.04 ms），由它推出来的"缩带宽 ⇒ +3.8 ms/帧"不成立（真实代价 ≈ 29 × 0.04 ≈ **1.2 ms/帧**）。
第九轮那组仍成立（两边像素与设备工作相同，差的确实是链路侧）。

**第八轮**：查询应答补上 `window`（`struct pud_qoid_state` 的 `u32 window = PUD_DELTA_WIN`）；
把主机侧 `delta_win` 故意设成 12345，查询一次后被纠正成 **32768**。默认 `DECODER_TYPE=3` 的
局刷回归（5 种窗口 64x64 / 128x64 / 480x8 / 120x80 / 64x48）全部跑完、`submitted 300 ==
drawn 300`、`dropped 0`、`oversize 0`、吞吐 0.88~0.97 MB/s ⇒ 这几天加的东西没碰坏默认解码器。

## 危险项：持续负载下的静默冻结（根因指向显示总线的无界等待，**待真机验证**）

**症状**：主机 `bulk_write` 超时；设备 `submitted` 继续涨、`drawn` 停住、`dropped == 0`
（没有任何计数报警）⇒ 现场表现为"板子不动了但一切计数正常"，这是最坏的失败形状。

- 两次真实发生：`submitted 3 / drawn 0`（窗口搜索 + 每条带夹查询那轮）与
  `submitted 63 / drawn 60`（缩带宽测量那轮）。共同点是背靠背连续发很多小载荷。
- 第十二~十四轮约 **15,000 次发送未能复现**（同一会话连打 20×360 = 7200 次全过；每次复位后
  重连 20 个新会话 × 60 = 1200 次全过；更早还有 6 次洪泛全过）。统计上约 1/8 到 1/15000 不等，
  **罕见且触发条件未明**。
- **第十三轮对照组**：同一套洪泛脚本打默认 `DECODER_TYPE 3` 固件，3 × 360 = **1080 次发送
  全部通过**（`submitted 1080 == drawn 1080`、`dropped 0`）⇒ 当时据此判断"**不是**
  `PIO_USE_DMA` 那个'负载下显示通路卡住'的老毛病，卡死属于 type-6 路径（`tinyd` 的某类输入、
  或窗口 `memmove` 边界）"。
  **⚠ 这条推理已被修正（2026-10-02）**：它用的是当时约 **1/250** 的估计，而后来实测约
  **1/15000**；按后者，1080 次全过的概率是 ≈ **93%**，所以这组对照**没有排除共用通路**。
  见下面"2026-10-02 续查"一节。原判断保留在此，仅作记录。
### 2026-10-02 续查：签名指向**显示总线**，不是解码器

**签名先定范围。** 两次现场都是 `submitted − drawn == DECODER_FRAME_SLOTS`（3−0、63−60）。
结合任务循环（先扫槽再等信号量，`decoder.c`），"所有槽都忙"意味着解码任务**正卡在某一次
`decoder_drawimg_slot()` 里面**，而不是在等信号量：任务若在等待，槽不会全满。

**tinyd 已被排除（宿主机实测）。** 用宿主机驱动 + ASan/UBSan 直接打 `tinyd_inflate`：
- 可压缩数据（匹配密集，真正走 `decode_sym` 与距离/重叠分支）+ **真实字典**（不是全零）：
  15 组合法流与 zlib 逐字节一致；
- **匹配密集流的全部截断前缀**：0 处"返回 OK 但输出错"、0 卡死 —— 也就是说本次在研的
  `overrun` 防护确实成立（它修的是"截断流被当成功"的正确性问题，见下）；
- **8000 次随机变异**（改 0~40 字节）：0 卡死、0 越界、0 崩溃。
所以 `tinyd` 不是卡死来源；它的 `overrun` 防护是必要的**正确性**修复，但不是这个冻结的解。

**唯一无界的等待在显示通路上。** 沿 `decoder_drawimg_slot()` 往下，整条绘制路径上只有一处
没有超时的等待：

```
tft_async_video_wait()            (lib/pico-display-lib/drivers/display/tft.c:316)
  → i80_write_sync()              (drivers/bus/pio_i80.c:181)
    → i80_finish_pending()        (:69)
      → dma_channel_wait_for_finish_blocking(dma_tx)   ← 无超时
```

`i80_wait_idle(pio, sm)` 的 TX-FIFO 自旋同样没有上限。DMA/PIO 一旦不完成，解码任务就永久
卡在 `decoder_drawimg_slot()` 里 —— **症状逐条吻合**：`drawn` 冻结、槽全满、`dropped == 0`
（槽满后主机的 `bulk_write` 超时，不会再有新的 submit 去计数）、屏幕停住。

**这也修正了第十二轮对照组的结论**：那次用 3×360 次默认 `DECODER_TYPE 3` 全过，推出"卡死属于
type-6 路径"。但那个推理用的是**约 1/250** 的估计；按后来实测的 **~1/15000**，1080 次全过的
概率是 (1−1/15000)^1080 ≈ **93%** ⇒ 对照组**没有排除共用通路**。卡死是否与解码器有关，
现在**没有证据**支持。

### 已废弃的方案，以及为什么

- **原建议"在解码任务里复位游标 + 忙碌标志"不能生效** ✗：任务正是被卡住的那一方，它不会
  再回到循环里去执行复位。任何自动恢复都必须来自**被卡任务之外**（总线层的有界等待 + 中止，
  或看门狗复位）。
- **`tinyd` 的 `overrun` 防护保留**：它修的是另一个真问题（截断流返回成功、解出垃圾），
  宿主机实测全部 1405 类前缀已不再被误接受。

### 已落地：自愈看门狗（2026-10-02）

**设备现在能自己恢复，不必等人断电。** 实现在固件 `main.c` 的 `watchdog_supervisor_task()`：

- **监督任务必须在被卡任务之外**。它跑在 `tskIDLE_PRIORITY + 4`（decoder 是 +1、usb 是 +3），
  所以即使解码任务在自旋，tick 仍会调度到它。
- **判据是"有未完成的活且长时间没有进展"**：`submitted − dropped − drawn` 持续
  `PUD_STALL_MS`（1000 ms）不为零即判定停顿。
  **`dropped` 这一项不能省** ✗：`decoder_submit_frame()` 先 `submitted++` 再找空槽，丢帧的
  那笔**照样计入 submitted**，所以 `submitted − drawn` 一旦丢过帧就永不归零 —— 只用它做判据
  会在设备空闲 1 秒后**复位一台完全正常的设备**。这条已用宿主机状态机模拟验证：
  朴素判据在"发过 10 帧全丢后空闲"与"丢 3 帧"两种情况下都会误触发，带 `dropped` 的判据都不触发。
- **恢复动作是芯片的硬件看门狗**（`watchdog_enable(4000 ms, pause_on_debug=true)`），不是在
  被卡任务上复位状态：那个任务可能正握着面板总线传输到一半，由它之外的代码去拆是不安全的；
  而且硬件复位还能覆盖监督任务自己看不见的挂死。
- **停顿会留下证据**：原因写进 `watchdog_hw->scratch[0]`（魔数 `"PUDW"`）与
  `scratch[1]`（次数）—— scratch 跨复位存活，所以下次启动会打印
  `watchdog: recovered from N decoder stall(s) in a previous boot`，而不是看起来像随机重启。
  （槽 4 是 SDK 的；coremark 用 6/7；本固件用 0/1。）

**阈值的选择**：停顿 1000 ms 约为实测最长帧（整屏 73.7 ms）的 13 倍，看门狗 4000 ms 又是它的
4 倍。误复位比慢恢复更糟，所以取保守值。

### 仍然待办

1. **修总线（未做）**：把 `i80_finish_pending()`/`i80_wait_idle()` 的有界等待做出来 —— 超时就
   `dma_channel_abort()` + 复位 PIO SM + 重新初始化总线并计数上报。它把"复位"降级成"一次可见的
   坏帧"（不掉 USB、不失联），**与解码器无关**，对默认 `DECODER_TYPE 3` 同样有价值。
   改动在子模块 `lib/pico-display-lib` 里（按它的 `AGENTS.md`：先在那里提交，再更新固件指针），
   并且**必须在真机上验证**。
2. **看门狗与根因都未上板验证**：只能确认编译、链接与静态 RAM（+0），以及判据的逻辑经主机模拟。
   真机上要确认的是：`heap after init` 行仍在、停顿后确实打印 recovery 行并重新枚举。
3. **合入默认配置的前提**：看门狗已补，但**根因仍未在真机确认**。按上面的分析卡死**不是
   type-6 特有的**，所以第 1 项对当前默认配置也有价值。

## 查询命令 `PUD_CMD_GET_QOID`（0x05）

设备给每个被接受的条带记自增序号；窗口里"有货"是**解码完成之后**才置位的，所以主机在一条带
刚发完就查，可能只看到上一次的驻留。`struct pud_qoid_state`（**60 B**）上报
`magic`/`slots`/`serial[4]`/`len[4]`/`valid[4]`/`window`（`PUD_QOID_WINDOWS = 4`，
`DECODER_FRAME_SLOTS <= PUD_QOID_WINDOWS` 有 `_Static_assert`）。

- **设备侧已实现应答**：`src/cherryusb/usb.c` 的 `usbd_vendor_ep2_bulk_in_fsm()` 处理
  `PUD_CMD_GET_QOID`，`decoder.c` 的 `qoid_read_state()` 填状态；没有窗口的构建也回一个
  magic + 零 slots，好让主机区分"没有窗口"与"不认这条命令"。
- 上板实测：没有任何条带时查询返回 `{}`；发 3 条键帧后 `{1: 11744}`（序号与 QOI 长度一致）；
  查询夹在每条带之间 30 次全部完成、不卡；设备侧 `submitted 63 == drawn 63`、`dropped 0`。
- **一次查询约 2.9 ms**（30 次"查询+发送"220.4 ms 对纯发送 133.0 ms），比控制传输 0.14 ms
  贵二十倍 ⇒ **绝对不能每条带查一次**（+25~70%）；要用驻留信息时最多**每帧查一次**。
- **已同步（2026-10）**：原来两处漂移都已修 —— `include/pud.h` 的 "NOT ANSWERED YET" 注释
  改成了它现在的行为（已应答；没有窗口的构建回 magic + 零 `slots`），驱动仓
  `notes/usb-protocol.md`（权威定义）也补上了 `0x03`/`0x04`/`0x05`、`decoder_type=6` 与
  16 B 子头的布局。
- **驱动侧编码器已实现并上机验证（2026-10-02）**：内核 zlib 没有 `Z_FIXED`（`tinyd` 只解固定
  Huffman / stored）也没有 `deflateSetDictionary`（字典是这编解码器的全部意义），所以驱动自带
  `tinyc.c` —— 本解码器的编码镜像。字典靠**设备分配的 serial** 指名，驱动记最近 3 条同矩形条带；
  序号只在 flush 成功后消耗。
  **真机实测（RK3588，内核 6.1.172，计数器经 SWD 读出）**：kiosk（cage/Wayland）连续渲染
  4490 条带，`qoid_bad == 0`（tinyc 产出的码流**全部**被设备解出）、`dropped == 0`、
  `qoid_mismatch` 稳定在 4（启动瞬态后不再增长）、`qoid_oversize == 0`。
  实现细节与已知缺口见驱动仓 `notes/encoders.md`。
- **分带受"窗口半宽"约束，不只是传输上限**（真机踩出来的坑）：窗口是 `[历史][输出]` 各一半，
  所以**本条带的 QOI 流本身**也必须 ≤ `PUD_DELTA_WIN / 2`（RP2350 16384 B）。QOI 最坏 3 B/px
  ⇒ 每带最多 **5456 px**，比传输上限允许的 21835 少近四倍。超了设备整条丢弃并计
  `qoid_oversize`——**主机看不到**，那块面板静默停止更新。
  现象：**kiosk 正常、切 GNOME 后整块黑**（cage 只报小块 damage，Xorg 首次提交是整屏 480×320）。
  收窄分带后强制 modeset 的 30 条带全部绘制、`qoid_oversize` 零新增。
- **GNOME 跑 X11 时不会往这块面板呈现**：Xorg 会把它配成第二台显示器、也做过 modeset，但之后
  **不再提交任何帧**（不是"没有 damage 所以不刷"——本驱动的无 clip 行为是整屏刷新）。同一台机器上
  cage/Wayland 正常，所以要用 GNOME 得用 **Wayland 会话**。
- `0x03`–`0x05` 三条命令驱动仍不发送。

## 已知缺口与未做

- 主机要复现槽位轮转就得知道 `DECODER_FRAME_SLOTS`，而 `PUD_CMD_GET_CAPS` **没有上报它** ⇒
  原型里主机侧配置成 3；配错不会花屏，只会让 `qoid_mismatch` 计数。
- `decoder_submit_frame()` 丢帧时**照样**消耗序号，之后的槽位模型会错位、后续 DELTA 被
  `dict_serial` 校验一路拒收（安全：计数丢弃，不花屏），主机发一轮键帧即可恢复。
  流控正常时 `dropped == 0`，所以"看到 `qoid_mismatch` 涨"要先看 `dropped`。
- 修好后的 **A/B 复测**（游标那版 16.53 → 4.72 ms 机制数字仍有效，但应该用当前固件重测）。
- RP2040 上板；用 `PUD_CMD_GET_QOID` 做决策前要确认目标带**已经解完**。
- 照片/噪声内容超半窗会被拒（面板那块不更新）；主机现在只打印一次警告，改成**报错**还是
  **自动退回**别的码流是产品决定（设备同时装两个解码器现在做不到）。
