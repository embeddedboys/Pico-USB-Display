# EP1 载荷在持续负载下按 64 字节粒度被破坏（未定位）

> 洪水负载下偶发收到"丢掉 64 字节整数倍、后面数据整体前移"的流；设备侧没有任何报警，
> 只有 `DECODER_TYPE 6` 的子头 + `tinyd` 校验会把它计数成一次拒收。

## TL;DR

- **现象**：12 000 与 60 000 次发送各抓到一次 `DECODER_TYPE 6` 拒收（`qoid_bad +1`）；帧头矩形/长度校验通过、`dropped 0`、`ep1 bad` 未动、`CFSR 0`。
- **结论**：收到的是**丢包后整体前移**的流（丢的是包、不是比特 —— USB 每包有 CRC，且 `size` 字段完全正确）。
- **影响面**：**所有解码器**都走这条重组路径；若被破坏的载荷恰好通过帧头校验，注入的是一帧错误画面而不是被丢弃的一帧。
- 下一轮第一件事：主机抓 `usbmon` 的同时跑洪水，把线上字节与载荷文件逐字节比；固件侧加全量取证。

## 现象与取证

本机洪水（480×11 键帧条带、无间隔、pyusb 直连、本机 3-6 根口），12 000 与 60 000 次发送时
各抓到一次 `DECODER_TYPE 6` 拒收（`qoid_bad +1`）。设备**完全不报警**：帧头的矩形/长度校验
通过、`dropped 0`、`ep1 bad` 未动、`CFSR 0`。

取证用的是 `decoder.c` 里的 `g_qoid_reject`：size / slot / 字节和 / 每 1 KB 的 FNV /
头尾各 16 B；载荷用子头的 `reserved` 字段带条带号。生成、洪水与快照分析用的是一次性脚本
（**未入库**），要复现得按本节描述重写。

| 现场 | 观察 |
| --- | --- |
| A（12 000 次） | `rc = -3`（tinyd：match 指到窗口起点之前）；size 与某条带相同，**字节和与任何发出载荷都不匹配** |
| B（60 000 次） | `rc = 0x101`（子头 magic 不对）；头 16 B **逐字节等于 `band02[64:80]`**；blk[1] = `band02[1152:2176]`、blk[2] = `band02[2176:3200]`（**错位 +128**）；blk[0] 在任何载荷的任何偏移都找不到；字节和 420388 对 421183（只差 795） |

⇒ 收到的是**丢掉 64 字节整数倍、后面数据整体前移**的流：先在载荷最前面丢 64，再在前 1 KB
内又丢 64。**丢的是包、不是比特** —— USB 每个包有 CRC，线上位错会被丢弃重传，而 `size`
字段完全正确。

## 影响面

所有解码器都走这条重组路径；`DECODER_TYPE 6` 只是唯一会把它**计数**出来的（子头 + tinyd
校验会拒收）。它很可能就是 type 6 那些零散 `qoid_bad`/`mismatch` 的来源；而若被破坏的载荷
恰好通过帧头校验，注入的会是一帧**错误画面**而不是被丢弃的一帧。
与 [qoid.md](qoid.md) 的"静默冻结"是否同源，**未验证**。

## 已排除 / 未排除

- 主机侧**没做到证据级**：CRC + libusb 同步写会先把数据拷进自己的缓冲 ⇒ 推断主机无责，
  但要证实得抓 `usbmon`（本机 `sudo` 要密码，当前环境做不了）。
  **下一轮第一件事**：主机抓 `usbmon` 的同时跑洪水，把线上的字节与载荷文件逐字节比。
- 端口路径**读下来没有明显的顺序错误**：`lib/CherryUSB/port/rp2040/usb_dc_rp2040.c` 的 EP OUT
  是"先 `memcpy` 拷出、再 `usb_start_transfer()` 重新 arm"（`usb_handle_ep_buff_done()`）。
  剩下的嫌疑：重组层（`usb.c` 的 `got/total` 与 `ep1_read_more()` 的指针推进）、
  DPRAM 单缓冲（[pitfalls-toolchain.md](pitfalls-toolchain.md) 5.1）。
- **下一个刀口**：给固件加**全量取证**（被拒载荷的前 4 KB 复制进一块静态缓冲）⇒ 直接看
  "丢掉的那 64 字节位置上到底是什么"（上一条传输的残留？还是新包的数据？）⇒ 一次就能把
  "重组算错指针"和"控制器吞包"分开。

## 顺带修掉的：`tinyd` 会把截断的流当成成功

**已修（工作区未提交）**：1405 个前缀全部被接受为 `TINYD_OK` 并输出垃圾。根因是
`br_drop()` 在 eof 后让 `n` 无符号下溢，`eof && n == 0` 那道 guard 永不成立；另外内层循环
会用"累积器空时 `idx = 0` 正好是固定码表的 EOB"提前 `break`。修法是显式 `overrun` 标志 +
三处检查（外层 guard、内层循环头、函数出口）。

验证：1405 个前缀**全部拒绝**；正向用例（带字典 delta / stored / level 9 / 补齐字节）与
zlib **逐字节一致**；动态 Huffman 仍然拒绝；超窗仍然 `OVERFLOW` 不截断。
**这条同时把上面那种被破坏的载荷从"rc 0 画垃圾"变成"计数拒收"。**
