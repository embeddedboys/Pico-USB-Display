# 桌面负载下的编解码器选型

> 本项目面向桌面（配合 DRM 驱动），主负载是**局部刷新**：真实内容上 QOI 更快、载荷更小；
> **引用"QOI 更快"时必须带上内容** —— 合成桌面上 LZ4 在 8 个区域里有 6 个反而更小。

## TL;DR

- 桌面区域实测（真实 4K 截屏）：QOI 每个矩形比 RLE/LZ4 快 **21~32%**，因为它载荷最小；三者都跑在链路极限上，时间 ≈ 载荷 ÷ 带宽。
- 同源复量：真实内容整屏 QOI 131183 B / 138.99 ms 对 LZ4 183549 / 194.23（QOI 快 27~35%），但合成桌面上 LZ4 在 8 区域里 6 个更小 ⇒ 选型依赖内容。
- **QOI+deflate level 6 在两个内容的每个区域都最小最快**（真实整屏 −23%、合成 −26%）。
- **给设备计时必须把编码放在循环外**：早期把 Python 编码算进去，得出的"LZ4 快 6~20%"是错的。
- RLE 在高熵内容上反而比 QOI 小 1.45 倍（literal run 把 128 像素摊到一个控制字节），但结构化内容全面落后。

## 真实桌面区域对比（2026-09 实测）

项目面向桌面，主负载是**局部刷新**：整屏照片/噪声测试**不代表**它。`tools/desktop_codecs.py`
按"桌面会脏的矩形"逐个比较，内容用板子自己的真实桌面 —— HDMI 会话截屏（3840×2160），
两种用法各测一遍：`real_downscaled`（整屏缩到 480×320）与 `real_crop`（4K 里 1:1 裁 480×320，
原生分辨率 UI、文字可读）。

板上实测（20 帧中位值，间隔 3 ms，`--device`；**编码在计时循环外**、单独列出）：

| 区域 | 像素 | QOI | RLE | LZ4 | QOI 载荷 | LZ4 载荷 |
| --- | --- | --- | --- | --- | --- | --- |
| 面板条 480×24 | 11520 | **3.20 ms** | 5.15 | 4.50 | 3318 B | 4823 B |
| 文本行 272×14 | 3808 | **2.94** | 4.94 | 3.94 | 2878 | 4128 |
| 列表行 240×16 | 3840 | **1.84** | 3.06 | 2.49 | 1707 | 2523 |
| 标题栏 260×22 | 5720 | **3.52** | 6.20 | 5.09 | 3649 | 5233 |
| 窗口空白体 260×60 | 15600 | **6.89** | 11.88 | 10.04 | 7435 | 10968 |
| 整窗 288×140 | 40320 | **25.92** | 41.94 | 32.61 | 26391 | 35449 |
| 壁纸条 480×60 | 28800 | **13.42** | 22.94 | 19.77 | 14398 | 20586 |
| 整屏 | 153600 | **75.70** | 120.97 | 100.92 | 76503 | 107650 |

**QOI 每个矩形都快 21~32%，因为它载荷最小（少 15~35%），而三者都跑在链路极限上**：
实测带宽 QOI 1.01、LZ4 1.07、RLE 1.09 MB/s —— 链路约 1.1 MB/s，时间基本就是 `载荷 ÷ 带宽`。
桌面内容（抗锯齿文本、阴影、半透明、照片壁纸）**不是** LZ4 擅长的长重复模式，而是 QOI 的
index/diff/luma 更能描述的东西。

设备侧（`DECODER_STATS` 的 `draw_us`，即解码+刷屏，不含主机）每帧：

| 整屏 153600 px | QOI | RLE | LZ4 |
| --- | --- | --- | --- |
| 设备忙 | 5.5 ms | 2.4 ms | 2.2 ms |

远小于各自的链路时间（76 / 121 / 101 ms），所以**当前是链路受限，QOI 的解码慢不构成问题**；
但这是它唯一的隐患：链路一旦提速（USB 高速、更快面板），QOI 会先变成设备侧瓶颈。

**选型结论（设备侧单独看）**：桌面负载上 **QOI 最快**；纯照片整屏也是 QOI 的场合。
LZ4 的价值不在性能，而在**内核侧** —— 它是内核自带的，驱动不必 vendor 编码器源文件
（见 [todo.md](todo.md)）。要换 LZ4 就得接受桌面内容上约 **25% 的额外延迟**
（100.92 vs 75.70 ms 整屏），这笔账按项目优先级算。

## 测量纠正（重要）

第一版 `desktop_codecs.py --device` 用 `send_rgb565()` 计时，而它**在计时循环里做编码**。
`pud_usb.py` 的 QOI/RLE 编码器是手写 Python（实测整帧 **43.8 / 54.8 ms**），LZ4 走 liblz4
（**2.6 ms**），于是量到的是"Python 解释器 vs C 库"，当时得出"LZ4 快 6~20%"的结论是**错的**。
现在改成先把每个 band 编码好、再用 `fps_bench.measure()`（只发 `send_raw`）计时，并把编码
耗时单独打印成一列。**内核驱动里两边都是 C（驱动自己编码），不存在这个偏差。**
`img_viewer.py` 打印的 MB/s 同理不是链路速度（含 Python 侧图片加载与 QOI 编码）。

## 同源复量：四种码器、两个内容、一把尺子（2026-09-30）

上面那张表和"选型结论"分别用了两种内容、各自与自己的 QOI 比。用**同一个回路**（每带一次
`send_raw`，20 帧中位值，编码在计时循环外）重测，**所有行都是设备实测**：

**A. 合成桌面（`desktop_frame()`，照片壁纸）**

| --- | --- | --- | --- | --- |
| 面板条 480×24 | 2122 B / 2.36 ms | **1303 / 1.53** | 1728 / 1.98 | 2664 / 2.93 |
| 文本行 272×14 | 2010 / 2.28 | **1078 / 1.29** | 1262 / 1.42 | 2646 / 2.92 |
| 列表行 240×16 | 682 / 0.81 | **453 / 0.62** | 591 / 0.73 | 937 / 1.06 |
| 标题栏 260×22 | 735 / 0.95 | **534 / 0.72** | 699 / 0.81 | 1048 / 1.18 |
| 窗口空白体 260×60 | 2612 / 2.97 | **1261 / 1.51** | 1853 / 2.08 | 3648 / 3.97 |
| 整窗 288×140 | 18124 / 19.38 | **9560 / 10.45** | 12474 / 13.38 | 24383 / 25.89 |
| 壁纸条 480×60 | 19252 / 20.52 | **15430 / 16.55** | 27710 / 29.45 | 32190 / 34.19 |
| 整屏 | 93893 / 100.02 | **68874 / 74.03** | 114153 / 121.15 | 147492 / 156.24 |

**B. 真实内容（`assets/xfce.jpg` 缩到 480×320，即 `desktop_codecs.py --image` 的用法）**

| 区域 | QOI | QOI+deflate L6 | LZ4 |
| --- | --- | --- | --- |
| 面板条 | 8200 B / 8.78 ms | **6157 / 6.63** | 12673 / 13.47 |
| 文本行 | 3522 / 3.83 | **2674 / 2.99** | 4916 / 5.36 |
| 列表行 | 3305 / 3.64 | **2260 / 2.54** | 4792 / 5.19 |
| 标题栏 | 4919 / 5.34 | **3369 / 3.75** | 7193 / 7.72 |
| 窗口空白体 | 14411 / 15.28 | **10973 / 11.71** | 20218 / 21.40 |
| 整窗 | 35997 / 38.06 | **26284 / 27.93** | 49450 / 52.28 |
| 壁纸条 | 24528 / 26.13 | **19379 / 20.71** | 35208 / 37.33 |
| 整屏 | 131183 / 138.99 | **100326 / 106.85** | 183549 / 194.23 |

三条结论：

1. **时间就是载荷**：两组的每一行都落在 **0.73~0.95 MB/s** 的同一条线上，码器排名因此完全
   等于载荷排名；与 QOI 的载荷比 0.715（真实内容）与 0.733（合成桌面）分别对应实测的
   −23.1% 与 −26.1%。
2. **QOI+deflate level 6 在两个内容的每个区域里都最小最快**（真实整屏 −23%、合成 −26%，
   单区域最好 −49%）。这是新增结论：之前只测过合成桌面的照片带（那里 deflate 几乎无收益），
   **真实桌面上整图也有 ~23%**。
3. **QOI 与 LZ4 的胜负依赖内容**：真实内容上 QOI 每个区域都快 27~35%（载荷比 0.715 与那份
   4K 内容的 0.711 只差 0.6%），而合成桌面上 **LZ4 在 8 个区域里有 6 个反而更小**
   ⇒ **引用"QOI 更快"时必须带上内容**。绝对 MB/s 是会话属性（这一轮 0.94、区域对比那次
   1.01~1.09），只有比值能搬。

RLE 载荷用 `tools/build/pudcodec`（同一份 liblz4）逐带生成 —— 本机没有 python 的 `lz4`
绑定，`desktop_codecs.py` 的 LZ4 通道需要它（见 [todo.md](todo.md)）。

## 怎么取真实桌面内容（板上 GNOME/Wayland 的三个坑）

- GNOME 的截图 D-Bus（`org.gnome.Shell.Screenshot`）**拒绝跨会话调用**：ssh 的会话与图形
  会话不是一个 session，报 `Screenshot is not allowed`，`systemd-run --user --scope` 也一样；
- `/dev/fb0`（`rockchipdrmfb`）读到的是**全黑** —— 合成器扫的是自己的 GBM buffer，fbdev
  模拟那块不是活画面；
- 所以用**键盘 PrintScreen**（GNOME 存到 `~/Pictures/Screenshots/`），拷出来传给
  `desktop_codecs.py --image` 即可。

## 批次乒乓值多少（`PUD_DECODER_PINGPONG` A/B）

QOI/RLE 的回调解码器可以只用一块累积缓冲（每批都要等它刷完）或用两块乒乓（下一批的解码和
上一批的刷屏重叠）。默认 `1`，关掉还能省 **7680 B/活跃解码器**（QOI 构型实测 `.bss`
152132 → 144456）。

**设备侧确实有效**（`DECODER_STATS` 的 `draw_us`，解码+刷屏，不含主机；每帧之间 2 ms 间隔）：

| 载荷 | 内容 | 乒乓开 | 乒乓关 | 差 |
| --- | --- | --- | --- | --- |
| QOI 2634 B | 纯色整屏 | 765 µs/带 | 1110 µs/带 | **-31%** |
| RLE 3638 B | 纯色整屏 | 491 µs/带 | 811 µs/带 | **-39%** |
| QOI 76503 B | 真实桌面整屏 | 5498 µs/帧 | 5897 µs/帧 | -7% |
| RLE 131723 B | 真实桌面整屏 | 2424 µs/帧 | 2777 µs/帧 | -13% |

**端到端在那个负载下量不到差别**（0.1~0.7%，在噪声里）：纯色整屏 20.95 → 21.09 ms、
真实桌面整屏 113.37 → 113.76 ms。设备侧成为瓶颈时才看得到（早先异步刷新那次：帧率
123.8 → 177.5 fps，见 [qoi.md](qoi.md)）。

> 这是**回调版**解码器的账。QOI 现在默认走**非回调 + band 乒乓**（[qoi.md](qoi.md)），批次
> 乒乓对它不再适用；`PUD_DECODER_PINGPONG` 仍管着回落到回调版的那条路径和 RLE。

## RLE 与 QOI 的格式与压缩率

RLE 来自独立仓库 `rgb565-rle`（MIT），vendored 在 `src/decoders/rle/`，与该仓 `master`
逐字节一致（含 run 批量填充优化）；QOI 同理（`rgb565-qoi` → `src/decoders/qoi/`）。
两个库各有一个**放置钩子**（`RGB565_RLE_SECTION` / `RGB565_QOI_SECTION`），本项目用它把解码
循环放进 SRAM（`PUD_CODEC_IN_RAM`）—— **要改行为就先改上游再整体拷回**。接口形状一样
（回调 + 双缓冲 ping-pong），**零静态状态**。

| | RLE | QOI |
| --- | --- | --- |
| 格式 | 4 B 像素数 + 重复 [控制字节 + 数据] | `q565` 魔数 + 逐 op |
| 理论最坏 | 3 B/px | 3 B/px（所以分带规则不用改） |
| 480×320 纯色 | 3638 B | **2634 B** |
| 480×320 渐变 | 49992 B | **32873 B** |
| 480×320 照片 | 226758 B | **131183 B** |
| 480×320 **噪声** | **308433 B** | 444550 B |
| 端到端 480×320（分带） | 6.73 / 48.36 / 207.0 / 275.9 ms | 7.00 / 35.70 / 127.4 / 422.7 ms |
| 端到端 160×120（单次传输） | 0.46 / 2.32 / 9.10 / 12.00 ms | 0.53 / 1.69 / 5.58 / 17.95 ms |
| 静态 RAM | 与 QOI **完全相同**（整机构型 222676 B） | — |
| `decoder_task` 栈峰值 | 464 B | 496 B |
| flash（text+data） | 177888 B | 158992 B |

（端到端四列依次是 solid / gradient / photo / noise；由 `tools/codec_compare.py` 测，
内容是同一份，只换编码器。）

**结论：链路是瓶颈（EP1 约 1.1 MB/s），端到端快慢基本由压缩率决定。** 结构化内容 QOI 小
1.4~1.7 倍（更快）；**高熵内容 RLE 反而小 1.45 倍** —— 它的 literal run 能把 128 个像素摊到
一个控制字节（实测噪声 2.01 B/px），而 QOI 对高熵像素只能发 3 B/px 的 RGB565 op。解码本身
两种都很快（160×120 单次传输差距 0.1~6 ms），所以选型看压缩率而不是解码速度。

RLE 是**无损**的，而且**板上验证过**：开机 logo 整帧 480×320、153600 个像素与参考逐像素
完全相等（QOI 也是精确相等；tjpgd/JPEGDEC 是 ±1 LSB）。

### RLE 的 run 批量填充（2026-09 实测）

上游 RLE 的 run 体是逐像素 16 位 store，而一个 run 最多 128 像素 —— 循环开销要按控制字节
摊薄之前得先付 128 次。改成每次处理 4 个像素：重复 run 存一个"同一像素写两遍"的 32 位字，
literal run 直接字节拷贝（小端目标上压缩数据本身就是像素值），尾部按 2 或 1 个像素收尾。
**只动 run 体**，缓冲填充点、flush 时机、回调参数都没变。

板上 A/B（**当时是 150 MHz** RP2350；现在是 225 MHz；480×320 按 8 行分批，交替烧写、
同一主机同一脚本、`--frames 100`，"解码+刷屏"取 `draw_us` 每帧均值）：

| 内容 | 解码+刷屏（改前 → 改后） | 端到端（改前 → 改后） |
| --- | --- | --- |
| solid | 4460 → **3985 µs**（-10.7%） | 6.00 → 6.00 ms |
| gradient | 15525 → 15457 µs（-0.4%） | 48.03 → 48.26 ms |
| photo | 40708 → 39691 µs（-2.5%） | 207.68 → 207.21 ms |
| noise | 46230 → 45156 µs（-2.3%） | 276.32 → 276.03 ms |

**设备侧更快，端到端看不出来**：四档里三档 USB 受限；只有 run 重的纯色解码占比大，省下的
0.5 ms 也基本被分批流水线吸收。保留它的理由是设备侧余量，不是现在的帧率。
正确性：与改前对拍 **28560 例**（7 种内容 × 宽 1~480 × 高 1~320 × 10 种批容量 ×
单缓冲/乒乓），整帧解码结果与完整回调事件序列逐位相同；板上开机 logo 153600 像素 0 差异。

> 这份改动已提交到 `rgb565-rle` 仓（**未推送**）。重新 vendor 时要注意：从远端拉会丢掉它，
> 直到该提交推上去为止。

## 两个不背锅的"优化"

**`PUD_MAX_TRANSFER` 不是瓶颈**：链路实测 **1.11~1.13 MB/s**，从每帧 11 KB 到 444 KB 都是平的
（= 全速理论上限 1.216 MB/s 的 93%），CherryUSB 端口只给每个端点 64 B DPRAM 单缓冲
**不是瓶颈**。把 `PUD_MAX_TRANSFER` 从 64 KB 降到 32 KB：省 109 KB RAM，但设备侧多花 2~3%，
而且**小载荷反而明显变慢**（纯色 4.6 → 6.5 ms/帧，band 数 8 → 15）。128 KB 之前量过是持平的。
**结论：RP2350 保持 64 KB、RP2040 保持 32 KB。**

**存一整屏省不掉 `set_addr_win`**：每次 flush（一次 `set_addr_win` + 起一次异步像素 DMA）实测
**22 µs**（照片档 `flush_us` 3519 µs / 160 次），一帧 8 个 band 合计 **176 µs ≈ 设备侧 0.8%**，
端到端 86 ms 里是 0.2%。省不掉**主机侧的 EP0 窗口请求**（按"传输"算，实测 0.141 ms × 8 =
1.1 ms/帧 ≈ 1.3%）。设备**不知道一帧的多个 band 何时结束**（协议里每个传输都是一份独立的、
自包含的矩形图像），即便有全屏缓冲也不能把 8 次 flush 合成 1 次 —— 除非协议加"帧边界"标记。
内存本来也不够（现在 RAM 312336 B = 59.6%，再加 300 KB 会到 ~605 KB > 512 KB）。**不做。**
