# Summary

在陌生仓库里**先建立可靠的工程模型，再改代码**。默认流程是
`RECONNAISSANCE → MODEL → IMPLEMENT → VERIFY`，而不是"读一个文件就猜、改完编译、编译不过再补"。

核心是三条：**先理解再修改**；**Evidence before assumption**；**仓库证据优先于个人直觉**。

证据优先级：项目代码 > 项目测试 > 构建/配置 > 项目文档 > 权威外部文档 > 通用工程经验 > 个人假设。
**不能用经验替代仓库里已经存在的事实**（例如"Linux 驱动通常这样做"不是改这个仓库的理由）。

**Unknown must remain unknown**：未确认就写 `UNKNOWN`，不写 `PROBABLY/LIKELY/I ASSUME`。
流程是 Unknown → Search → Read（定义/调用者/文档/测试）→ Evidence → Conclusion；
仍无法确认就**记录不确定**并选**最小的安全改动**。

**不要把局部上下文当系统上下文**：看到 `foo_init()` 不能推断它只调用一次、可阻塞、可睡眠、
失败可忽略、调用者拥有资源。必须继续找 definition / callers / callees / callbacks / 相关结构 /
初始化路径 / 退出路径 / 错误路径 / 测试 / 配置。

**现有模式优先于自创模式**：改之前先搜"这个仓库已经怎么做这件事"。
**最小且有依据的改动**；**不要用补丁掩盖理解错误**——编译通过不等于理解正确。
改接口前搜 caller/callee/callback，改生命周期前看初始化与释放。

**Definition of Done**：能**不靠猜测**回答——项目做什么、怎么构建、执行从哪开始、
哪个子系统实现该行为、控制流与数据流怎么走、涉及哪些状态与资源、资源归谁、
有什么配置或硬件依赖、该 follow 哪个既有模式、怎么验证、还有哪些假设不确定。
答不上来就**没完成探索**。
