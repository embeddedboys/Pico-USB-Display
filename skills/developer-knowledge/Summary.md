# Summary

知识库的目标是让读者**10 秒内**知道"这解决什么问题、结论是什么、我该做什么"。

**结构（首屏规则）**：`一句话结论 → TL;DR → 现象/背景 → 结论/解决 → 为什么 → 复现/调试 →
边界与陷阱 → 相关`。没有内容的段落**不要留空标题**；小发现用"结论 + 解决 + 验证"三段式。

**信息预算**：简单事实 20–80 行，常规条目 50–150 行，复杂主题 100–300 行，
深度参考 300+ 需说明理由。超过约 150 行触发**压缩审查**（逐段问"这句有可复用信息吗"），
超过约 300 行考虑拆分。**一文档一问题**，大主题做索引，不做巨型文章。
更新既有文档用**合并后重写**，不要 `cat >>` 追加"更新于某日"式日记。

**事实分级必须可区分**：*已验证*（源码/文档/可复现实验/硬件实测支撑）直接陈述；
*观察*（某次实验的现象）注明测试条件；*假设*必须显式标"推测/未验证"，**不得写成结论**。

**反模式**：记录推理过程与失败时间线；贴整段日志（只留最小诊断片段）；
项目知识与通用知识混写；同一知识出现多个近义文档（先立唯一权威文档，其余用链接引用）。

**文档↔代码漂移检查（每次改知识库都做）**：运行时事实**以代码/配置为准**，
逐条核对文档断言的默认值、常量、开关与**特性是否存在**。发现漂移：以代码/实测为准修文档；
**不要删除历史测量数据**——把过时的那组标注"在配置 X 下测得"并指向当前配置，
删掉的只应是**过时的结论**；被否决的尝试若教得出可复用教训，**保留洞见、压缩叙述**。
每次改动都要给出"漂移清单"（漂在哪、以哪边为准、怎么修）。

**上游/vendored 内容不属于本知识库**：若一个文件的全部 git 历史都由工作区之外的作者提交，
它就是上游内容——**不要**为了满足行数预算去重写它，而应在索引里**显式登记**"上游、未改动"；
确实要引用就摘到我们自己的文档并注明出处，**不改原文件**。

索引文件（如 `notes/README.md`）只做三件事：**本知识库范围**、**文档索引表**、**维护约定**，
不超过约 60 行。
